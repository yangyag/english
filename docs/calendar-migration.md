# 기존 기록 이전과 복구

## 저장 방식

2026-09-06 한 단어 저장 변경: `init_db`는 기존 기록 이전 전에 `migrate_result_schema`를 실행하여 `batch_result.known`의 NOT NULL 제약만 해제한다. 신규 제출은 NULL(평가 없음), 복습은 true/false를 저장한다. 기존 신규·복습 응답과 `word_result` 원본은 변경하지 않는다. 새 테이블을 추가하지 않으며 반복 실행해도 결과는 같다. 과거 신규 응답을 기억률 분석에 섞지 않도록 종류를 필터링한다.

한 단어 버전 전환 시 백엔드를 먼저 갱신한다. API는 구 프론트의 10개 제출도 받아 신규 평가는 NULL로 저장한다. 새 프론트의 임시 저장 키는 `english-study-draft-v3`이며 구 `v2` 미제출 묶음은 자동 제출하지 않고 다시 시작하도록 안내한다. 구 임시 데이터는 삭제하지 않는다. 새 NULL 기록을 지원하지 않는 이전 코드로 단순 복구하지 않는다.

기존 `word`, `study_state`, `study_session`, `word_result`는 삭제하거나 재작성하지 않는다. SQLAlchemy `Base.metadata.create_all`이 `english.study_batch`, `english.batch_result`만 추가한다. `init_db`는 이후 하나의 트랜잭션에서 `migrate_legacy`를 실행한다. 실제 운영 실행은 이번 로컬 작업에 포함하지 않았다.

기존 응답을 세션·종류·실제 `studied_at`의 Asia/Seoul 날짜로 묶는다. `legacy:<session_id>:<kind>:<date>` 유일 키로 기존 그룹을 찾고 아직 없는 순위만 추가한다. 이전 직후 구 버전으로 복구하여 같은 날 추가 학습한 뒤 다시 전환해도 누락하지 않는다. 신규 첫 묶음만 들어 있는 `new_from_rank/new_to_rank`를 이용해 추가 학습 기록을 누락시키지 않는다. 조회만 하고 제출하지 않은 세션은 달력에 표시하지 않는다. 시간대가 없는 비정상 timestamp는 추측하지 않고 실패한다.

이전 중 실패하면 새 기록 삽입은 롤백되고 재시작으로 재시도할 수 있다. 테이블 생성은 먼저 완료될 수 있으나 원본은 그대로다. 서비스 쓰기와 이전은 같은 PostgreSQL advisory transaction lock을 사용한다. 기존 코드의 쓰기는 이 잠금을 모르므로 **전환 중 구 백엔드 쓰기를 중단해야 한다.**

## 알 수 없는 정보

- 기존 복습 응답의 정확한 원본 학습일은 저장되어 있지 않다. `source_date=NULL`로 이전하고 새로운 선택 복습의 완료로 간주하지 않는다. 첫 전환 후 이전에 복습했던 단어가 다시 제안될 수 있다.
- `study_state.next_rank`만 있고 응답 기록이 없는 단어는 누적 진도로 보존하지만 날짜를 만들어내지 않는다. 진도 화면의 `undated_learned_count`로 안내한다.
- 구 기록의 `study_date`와 실제 응답 시간이 다르면 실제 KST 응답 날짜를 사용한다. 새 학습에서는 시작일이 지난 미완료 제출을 거절한다.

## 추후 운영 전환 절차

1. 현재 코드 리비전과 프론트 이미지 태그를 기록하고 별도 이전 버전으로 보관한다. 새 프론트는 로컬에서 정적 생성·이미지 빌드한다.
2. 쓰기를 차단하고 구 `english-back.service`를 중단한다. 기존 컨테이너에서 DB `app`의 `english` 스키마를 `pg_dump -Fc -n english`로 백업한다. 비밀번호는 환경/기존 인증으로 전달하고 명령·문서에 넣지 않는다. 다른 서비스 스키마를 포함하거나 변경하지 않는다.
3. 백업을 별도 임시 로컬 DB에 복원해 복원 가능 여부와 기존 단어·응답 수, next_rank를 확인한다.
4. 새 백엔드로 `init_db`를 실행한다. 구 `word_result` 수와 `legacy:` 묶음에 속한 `batch_result` 수, rank·known·KST 날짜를 대조한다. next_rank가 전환 전과 같은지 확인한다. 초기 검증 시 신규 테이블에는 이전 기록만 있어야 한다.
5. 새 백엔드와 새 정적 프론트를 함께 활성화한다. 헬스, 월별 달력, 최신 신규·선택 복습 조회를 확인하고 쓰기를 개방한다. 생성/이전 실행은 운영 인증이 필요하며 여기서는 수행하지 않았다.

## 복구

- 쓰기를 개방하기 전 실패: 구 원본과 cursor를 변경하지 않았으므로 구 코드·프론트 이미지로 돌아갈 수 있다. 추가된 테이블은 남겨 두어도 구 코드에 영향을 주지 않는다. 원인을 수정한 뒤 이전을 재실행한다.
- 새 버전에서 학습한 이후 실패: 즉시 쓰기를 중단하고 **현재 english 스키마도 별도 백업**한다. 새 기록은 구 word_result에 없고 cursor는 전진했으므로 코드만 되돌려서는 이력이 보존되지 않는다. 가능한 경우 새 버전을 수정하여 복구한다. 백업 시점으로 되돌려야 하면 그 이후 학습을 잃는다는 점을 확인하고, 현재 백업의 새 기록을 보존·대조한 뒤 english 스키마만 복원한다. `app` 전체를 덮어쓰지 않는다.
- 이 문서는 전환 절차이며 자동 배포/자동 롤백 스크립트가 아니다. 실제 백업 복원은 운영 배포 단계에서 검증해야 한다.

## 로컬 근거

`back/tests/test_migration.py`: 추가 학습 20개, UTC→KST 날짜 경계, 응답 보존, 과거 복습의 NULL 원본 날짜, 반복 이전 0건, 날짜 없는 cursor 보존을 합성 데이터로 검증한다. 운영 기록을 복제하거나 수정하지 않았다.
